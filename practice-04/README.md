## Организация кода

- `task-service.js`: чистые операции над массивом задач (`addTask`, `updateTask`, `toggleTask`, `removeTask`, подсчёты). Не знает ни о DOM, ни о хранилище, ни о форме. Операции не изменяют входной массив и возвращают `{ ok: true, ... }` или `{ ok: false, error }`.
- `form-validation.js`: превращает сырые значения формы (строки или `null`) в проверенный объект `{ id, title, priority }` или в набор ошибок по полям. Понимает режим редактирования: тогда `id` берётся из `editingId`, а не из формы. Ничего не знает о DOM.
- `task-storage.js`: чтение, запись и удаление списка в JSON `{ version: 1, tasks }`. Проверяет прочитанные данные по схеме (тип полей, допустимый приоритет, уникальные `id`, версия), копирует только известные поля и никогда не выпускает исключения наружу: результат всегда `{ ok, ... }`.
- `task-view.js`: только отрисовка (карточки, сводка, пустые состояния), текст выводится через `textContent`.
- `main.js`: связывает всё вместе. Единственное место, где есть `window.localStorage`, чтение формы, обработчики событий и сообщения пользователю. Состояние (`currentTasks`, `currentFilter`, `editingId`) меняется только здесь, а `renderApp()` перерисовывает интерфейс по этому состоянию.

Функции хранения получают объект `storage` аргументом (а не берут глобальный `localStorage`), потому что в Node.js `localStorage` нет, и иначе их нельзя было бы проверить без браузера. Благодаря этому я проверил поведение при сбоях (хранилище бросает исключение, переполнение) подменным объектом. Данные из JSON проверяются до использования, потому что `JSON.parse` успешно разберёт любой синтаксически верный JSON (`null`, число, список с лишними полями), а приложение при этом сломается на первой же операции. Сначала нужно убедиться, что структура соответствует ожидаемой.

Замечание про длину 101: поле имеет `maxlength="100"`, и при обычном вводе (в том числе при автоматическом заполнении) браузер сам обрезает текст до 100 символов. Моя первая попытка проверить 101 символ это показала: значение обрезалось и задача добавлялась. Поэтому в итоговой проверке 101 символ записан в поле программно, в обход `maxlength` (так бывает при подмене значения через консоль), и ошибка выдана прикладной проверкой. Это как раз пример того, зачем нужна проверка в коде помимо атрибутов HTML.

## Дополнительное задание

Выбрано расширение А: черновик формы создания. Допущение: из предложенных вариантов я взял именно его, так как оно лучше всего показывает работу с `localStorage` и ошибками хранилища.

Правила (модуль `task-draft.js`, формат `{ version: 1, draft: { id, title, priority } }`, все значения строки, как в полях формы):
- черновик хранится отдельным ключом `<ключ задач>:draft`, не смешивается со списком задач; у общего набора и варианта свои черновики;
- сохраняется при вводе в режиме создания; пустая форма означает «черновика нет» (ключ удаляется);
- восстанавливается при загрузке и после выхода из режима редактирования;
- удаляется после успешного добавления и при сбросе данных;
- в режиме редактирования не читается и не меняется;
- повреждённый или неверный черновик не применяется, удаляется, форма остаётся пустой, показывается предупреждение; недоступное хранилище не вызывает исключений.

Проверки расширения (Node: Расширение 1–3; браузер: Расширение 1–5):
1. ввод id и названия, перезагрузка: поля восстановлены, список задач не изменился;
2. успешное добавление и сброс данных очищают черновик;
3. режим редактирования не трогает черновик;
4. в черновик записан неверный JSON: он удалён, форма пуста, предупреждение показано;
5. общий набор и вариант имеют разные черновики.

Во время проверок страниц `checks.html` и `checks-own.html` черновик по умолчанию выключен (`draft=on` включает его для моих проверок), чтобы он не влиял на готовые проверки.

Найдено и исправлено при проверке этого расширения: если `localStorage` недоступен, сообщение «Черновик недоступен» затирало более важное «Хранилище не инициализировано» в строке состояния. Теперь предупреждения дописываются друг за другом (функция `showStorageWarning`). После правки обе проверки (`checks.html`, `checks-own.html`) и сценарий недоступного хранилища повторены: результат зелёный.

## Вывод

В работе я собрал приложение из отдельных слоёв: сервис, проверка формы, хранилище, отображение и `main.js`. Форма добавляет, редактирует и удаляет задачи, а состояние переживает перезагрузку. Общий сценарий методички и сценарий варианта 2 дали ожидаемые числа, все готовые и собственные проверки проходят (сервис 35, модули 27, браузер 23, свои 17 и 16).

Различие между тремя видами проверки я понял на примерах. Нативная проверка HTML (`required`, `maxlength`) срабатывает до `submit` и защищает только от очевидного, но пять пробелов она пропускает, а `maxlength` обходится программной подменой значения. Прикладная валидация (`validateTaskDraft`) проверяет смысл: тип `id`, дубликаты, длину после `trim`, режим редактирования; без неё в данные попали бы строки вместо чисел. Проверка данных из хранилища нужна на другом входе: `JSON.parse` не гарантирует структуру, поэтому запись проверяется по версии и схеме, а при любой проблеме приложение запускается с исходным набором и предупреждением.

Ошибки и наблюдения по ходу работы: в проверке 101 символа сначала сработал `maxlength`, и это пришлось учесть в тесте; предупреждение о черновике затирало сообщение об ошибке основного хранилища (исправлено); после удаления карточки с клавиатуры фокус теряется (не исправлено, описано выше). Ограничения: запуск выполнен на Linux с Node.js v22.23.4 и автоматическим управлением браузером, снимок отладки собран из данных CDP.
