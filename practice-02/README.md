## 4. Модель данных и функции

Задача это объект `{ id, title, completed, priority }`:

| Поле | Правило |
|---|---|
| `id` | число, `Number.isSafeInteger(id)` и `id > 0`; уникальность проверяет `addTask`, так как знает весь список |
| `title` | строка, после `trim()` длина от 1 до 100, внутренние пробелы не меняются |
| `completed` | boolean; при создании всегда `false`; строки `"true"`/`"false"` и числа 0/1 отклоняются |
| `priority` | строго `"low"`, `"medium"` или `"high"`; по умолчанию `"medium"` (только для `undefined`) |

Разделение файлов:

| Файл | За что отвечает |
|---|---|
| `src/data.js` | данные: `demoTasks` (общий набор), `variantNumber`, `variantTasks` (шесть задач варианта 2) |
| `src/task-service.js` | девять функций логики, без `console.log` и без обращения к `document` |
| `src/task-extra.js` | расширение: `searchTasks` |
| `src/main.js` | сценарии и вывод (`console.log`, `console.table`), расчётов не делает |
| `checks.js` | готовые 35 проверок (не менялся) |
| `checks-own.js` | мои собственные проверки и проверки расширения |

Результаты функций:

| Функция | Успех | Ошибка |
|---|---|---|
| `createTask` | `{ ok: true, task }` | `{ ok: false, error }` |
| `findTaskById` | найденный объект | `undefined`, если не найдено |
| `getPendingTasks` | новый массив невыполненных | — |
| `getTaskTitles` | массив названий | — |
| `getTaskStats` | `{ total, completed, pending, progress }`, `progress` — число | для пустого списка `progress = 0`, а не `NaN` |
| `addTask`, `setTaskCompleted`, `renameTask`, `removeTask` | `{ ok: true, tasks }` — новый массив | `{ ok: false, error }`: плохие данные, дубликат id, задача не найдена |

Внутри модуля есть непубличные проверки `checkId`, `checkTitle`, `checkPriority`, `checkCompleted`: они возвращают текст ошибки или `null`. Это нужно, чтобы одни и те же правила использовались и в `createTask`, и в `renameTask`, `setTaskCompleted`, `removeTask`. Сначала проверяется тип, потом ограничения.

**Почему id не равен индексу:** индекс это позиция в массиве, и она меняется при удалении и вставке. После удаления задачи с id 7 задача с id 10 переезжает с индекса 3 на индекс 2, а её id остаётся 10. Если искать «по индексу», можно получить чужую запись или выйти за границу: в `demoTasks` четыре элемента, поэтому индекса 4 нет, а задача с id 4 лежит под индексом 1. Поэтому поиск идёт через `find` и строгое сравнение `task.id === id`.  
**Почему getTaskStats возвращает число, а не строку с процентом:** число можно сравнивать и использовать в расчётах, а строка `"50.0%"` для этого не годится. Форматирование (`toFixed(1)`, знак `%`) относится к выводу и выполняется в `main.js`. Округлять внутри функции нельзя: потеряется точность (для трёх задач и одной выполненной должно быть 33.333…, а не 33.3).  
**Какие объекты копируются при изменении задачи:** новый массив создаётся всегда (spread, `map` или `filter`). Новый объект создаётся только у изменяемой задачи (`{ ...task, completed }`). Остальные задачи в новом массиве это те же самые объекты, что и в старом. Поэтому ни одну задачу нельзя менять присваиванием `task.поле = ...`: изменилось бы и старое состояние. Это проверяет собственный случай «Свой 2» (`last.tasks[1] === tasks[1]`) и готовая проверка 33 с замороженными объектами.

## 8. Расширение

Выполнен **вариант А**: функция `searchTasks(tasks, query)` в `src/task-extra.js`, импортируется в `main.js`. Контракты девяти функций не менялись.

Контракт:
- запрос обрезается по краям (`trim`), поиск без учёта регистра по вхождению (`toLowerCase` и `includes`), регулярные выражения не используются;
- порядок задач сохраняется, объекты не копируются и не изменяются;
- пустой или пробельный запрос возвращает все задачи (новый массив);
- если `query` не строка (`null`, число), возвращается пустой массив. Это моё решение: в методичке поведение не описано.

## 9. Вывод

По сравнению с ПР1 логика вынесена из линейного скрипта в функции и модули: данные приходят аргументами, результат возвращается через `return`, а вывод вынесен в `main.js`. Ожидаемые ошибки возвращаются как `{ ok: false, error }`, а не бросаются исключением, поэтому вызывающий код обязан проверять `result.ok`. Неизменность данных проверена тремя способами: сравнением снимка `JSON.stringify` в сценарии, замороженными объектами в проверке 33 и моими проверками на равенство ссылок. Ошибка, которую пришлось исправить, это пропущенный `return` в стрелочной функции (эксперимент 2): без него функция молча возвращала `undefined`. Ещё поймал на практике, что копия массива через spread поверхностная: объекты внутри остаются общими.
